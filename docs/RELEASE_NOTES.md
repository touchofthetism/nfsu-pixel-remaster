## Install on the Pixel

1. Download the `NFSU-Remastered-…-arm64.apk` asset below on the phone and open it (allow installs from Chrome once).
2. Open **NFS Underground Remastered** → **Allow access to Internal storage/nfsu1** → confirm "All files access".
3. **Import game files (ZIP)** → pick `nfsu-gamedata.zip` (from the private *gamedata* release, downloaded on the phone, or straight from Drive). The launcher unpacks it into place and verifies `Speed.exe`.
4. **PLAY.** After a session, **Share diagnostics** sends the log ZIP wherever you like.

## What's new

### Build 13 — a Lock no longer waits for DXVK's cleanup
Install the APK over build 11 or 12; nothing else changes. Build 13 carries build 12's core placement (below), which no session has run yet: play a long session at your usual settings and share diagnostics.
- **What the 06:57 session showed** (build 11, 2992×1344, 2× MSAA, no frame cap, 26 minutes): 24 freezes of 20–87 ms inside one Direct3D call, a vertex‑buffer Lock, with the game thread spinning while DXVK's cleanup thread worked through up to 30 finished command lists.
- **Why.** When the game locks a buffer or texture the GPU has drawn with, DXVK makes it wait until the GPU is done with it, and it marks a resource done only when it resets the command list that used it. Build 11 moved those resets to the cleanup thread, so the frame signal no longer waited for them; but the done mark moved with them, and a Lock then waited for every reset queued before that list (on this GPU a descriptor‑pool reset now and then takes 150–260 ms).
- **The fix.** The queue thread now marks a list's resources done the moment the GPU finishes it, together with its signals; the cleanup thread keeps the slow part (command pools, descriptor pools, freeing objects), and the list keeps its references until then, so nothing is freed early. Later DXVK versions (2.x) split it the same way. With *GPU cleanup: In DXVK's queue* everything stays in DXVK's own order.
  - Tested on the build machine with the real patched queue code on a simulated GPU, under ThreadSanitizer and AddressSanitizer: resources are released 0.2 ms after the GPU finishes, with the signals, even with 32 lists waiting for the cleanup thread; in DXVK's own order a 15 ms reset holds the next lists' resources 15 ms. A copy without the fix fails the test.
  - The summary's *DXVK queue* line now counts the Locks that waited for the GPU, with their total and longest time.
- The two new build‑11 sessions show the X4 again: in the 06:57 session it ran at 1.4 GHz or less for 74 % of the time (58 FPS then, 95 FPS in the seconds it reached 2.6 GHz), which is what build 12's placement is for. At 2992×1344 with 2× MSAA the GPU was busy 71 % on average and above 90 % in 4 % of the seconds, so once the CPU is faster, *Anti‑aliasing Off* is the setting that leaves the GPU room.

### Build 12 — the game thread follows the fastest core
Install the APK over build 11; nothing else changes (mod packs, saves and options stay, *CPU placement* stays on *Fastest core*). Play as you like: long sessions are the ones that show it.
- **Why the frame rate fell after a few minutes.** The game is one busy thread, and since build 3 it has been pinned to the phone's biggest core, the Cortex‑X4 (cpu 7, 3.78 GHz). In build 11's six long sessions that core ran at 0.9–1.4 GHz for 60–84 % of the time the game was drawing, at every battery level from 84 % to 1 %, while the Cortex‑A725 cores carrying DXVK's threads averaged 2.1–2.5 GHz. The frame rate followed the X4: 83–98 FPS in the seconds it ran at 2.6 GHz or more, 46–57 at 1.4 GHz or less, with the GPU idle a quarter to half of the time. An X4 held to 1.15 GHz gets through less work than an A725 at 2.7 GHz.
- **The game thread now moves to wherever it runs fastest.** Once a second the game reads the clock each group of cores is allowed (the cap the phone's heat and battery limits set) and works out each group's speed: the kernel's own capacity figure for those cores (their work per clock at the top clock) scaled by the clock they may run at now. When an A725 group is at least 20 % faster than the X4 for three seconds in a row, the game thread moves there; it goes back to the X4 once that is as fast again for five seconds, and it never moves twice within ten seconds, so it doesn't shuttle. The little cores are never used. DXVK's threads move out of its way, and stay off the X4 while it is slow: the command stream is on every frame's path too, and an idle X4 cools sooner. A phone that doesn't show its caps keeps build 11's placement.
  - Tested on the build machine, the decisions alone and the whole placement with the phone's eight cores simulated, using the caps the X4 had on 2026‑10‑28: the thread leaves for cpu 5–6 on the third second at 1.15 GHz, goes over to cpu 2–4 when cpu 5–6 is capped harder, and comes home once the caps lift; an 8 % difference doesn't move it, a second move never comes within ten seconds of the last, and DXVK's threads get the right cores in each case. The keeper that has put back Android's replaced masks since build 11 takes each move as the new placement, so it neither undoes a move nor misses a mask Android replaces afterwards.
  - *CPU placement* has a third choice, *Biggest core only*: builds 3–11's fixed placement, for comparison.
- **You can watch it.** The full overlay's last line shows the cores the game thread is on, the clock they may run at and how often it has moved (`render cpu 5-6 (≤2688 MHz)  moved 3`). Each move is logged with the clocks of both groups. In the session summary the *CPU* line now gives the clock each core was allowed (average and lowest), and a new *Render thread* line says how much of the session the game thread spent on each group of cores and the frame rate it reached there.
- What to try: a long session at your usual settings. If it plays worse than build 11, set *CPU placement* to *Biggest core only* for the next one and share diagnostics after both.

### Build 11 — the freeze behind Present, and a placement that stays put
Install the APK over build 10; nothing else changes. Play as you like (any resolution, any cap): the next summary's *DXVK queue* line shows what the fix changed.
- **The 20–224 ms freezes, found and taken off the frame's path.** Build 10's watcher explained 319 Direct3D calls of 20 ms or more across its two sessions, nearly all of them Present. In 266 of them (83 %) the game was waiting on DXVK's queue thread, which was running with 11–19 finished command lists queued behind it, all already done on the GPU. That thread takes each finished list in turn: it waits for the list's GPU fence, fires its signals (one of them is "frame N is done", which the game's next Present waits for), then resets the list for reuse: two command‑pool resets, releasing every texture and buffer the list held, returning its descriptor pools, buffer slices, queries and events. The reset came before the next list's signal, so one slow reset held up every frame behind it. Resets now run on a thread of their own (*dxvk‑recycle*), and the queue thread fires each list's signals the moment the GPU finishes it. At half resolution the freezes came more often than at full (8.2 a minute against 5.9), so the GPU was never the cause.
  - **Tested on every push:** the real patched DXVK queue code runs on the build machine against a simulated GPU, under ThreadSanitizer and under AddressSanitizer. In a reproduction of the build‑10 freeze (one reset in 60 takes 15 ms), the time spent waiting for frame signals drops from 52 ms to 0.1 ms. The test also checks that every list is reset exactly once, only after its signals, in order; that no list returns to the recycler before its reset is done; that with 32 lists waiting, the queue thread does the next resets itself again; and that shutting down lets the cleanup thread finish every list it holds.
  - New option **GPU cleanup**: *Own thread* (default) or *In DXVK's queue*, the order of builds 1–10, for comparison.
  - DXVK keeps 32 command lists for reuse instead of 16, so a backlog no longer turns into creating and destroying them.
- **The thread placement stays put.** Nine minutes into build 10's 00:34 session, Android replaced the threads' CPU masks. For the remaining eleven minutes the game thread wandered over cpu 2–7 instead of staying on the X4, and DXVK's threads ran on the X4 beside it (the 00:55 session kept its placement throughout). The profiler now checks once a second and puts back any mask or priority that was replaced. Each restore is logged, and the *Threads* line counts them. A core paused for heat doesn't count as a lost placement, and a thread id the system hands to a new thread is never touched.
- **Each freeze explained further.** Every long‑call line now says, for the game thread and each DXVK thread, how many milliseconds it ran during the freeze and how long it waited for a free core, and how many lists were waiting for the cleanup thread. The summary's new *DXVK queue* line times every vkQueueSubmit, every list reset (and each of its four steps: command pools, resources, descriptor pools, buffers and queries), and the GPU fence waits. It also counts the command lists and descriptor pools created and freed.
- **Diagnostics that can't be misread.** Android keeps its crash log across installs, so the ZIP carried build 2's exit crash and the SIGSEGVs of builds 3 and 6, and an outside analysis of build 10 read them as build 10 being unstable. *report.txt* now lists each crash with the build it came from: by the library's build ID, which every session record now carries, or by the install date. A session whose record was never closed now says what ended it. Build 10's "NOT complete: crash or kill" was the app being swiped away from recent apps. The *hitches* count states its threshold (frames over 25 ms when uncapped), and resource lock calls are named in the long‑call line.

### Build 10 — less heat between races, and a name for the hitch
Install the APK over build 9; nothing else changes. For the next session: phone back at 120 Hz (Settings → Display → Smooth Display), Widescreen on, FPS limit 60 or 120 as you like.
- **The game no longer spins the fast core while it waits.** Build 9's profile put 10 % of all game time inside the game's own frame limiter, busy‑waiting, and in the menus nearly every frame. The launcher already sleeps after each frame until the next one is due. But the game measures each frame from the end of its own previous wait, so with both limiters running it saw every frame as short by exactly the time it had just spun, and spun a few microseconds longer each frame, until its spin had taken over all the time the launcher would have slept. With an FPS limit set, the game's own wait is now off and the launcher's sleep does all the waiting. The core idles in menus and the garage instead of running flat out, so the phone reaches the races cooler. The frame's time step is the same as before (never below 1/cap); *Unlimited* keeps the game's own limiter.
- **The hitch gets a name.** On a warm phone, frames of 80–160 ms come back every 6–30 s (every 7–8 s at the 120 cap), nearly all inside one Direct3D call of the game's frame function. A watcher on the profiler's 1 ms sampler now catches any Direct3D call that lasts 20 ms or more. It names the call (Present, EndScene, …) and records what was happening meanwhile: DXVK's command lists waiting to be submitted and on the GPU, whether Android was still taking the previous frame, and for the game thread and each DXVK thread its state, core and clock, plus the system call and kernel wait it was blocked in. The session summary gains a *Long D3D9 calls* line and a *vkQueuePresentKHR* line (how long Android took to accept each frame).
- **The audio limiter's volume comes all the way back.** Its release ran in single precision. The last steps toward full volume were smaller than a float can resolve, so after any loud moment the gain stopped 0.04 % short (−0.003 dB, inaudible), and the diagnostics counted every later second as "limited". It now runs in double precision.
- **Battery Saver** holds the screen at 60 Hz. Each session now records whether it was on, and while it is on the FPS limit follows the screen: build 9 rendered 88 FPS for a 60 Hz screen, a third of the work never shown. The chosen limit returns when Battery Saver goes off. (The 60 Hz in the build‑9 sessions was the phone's own refresh setting, which the summary's *Panel refresh* line shows.)
- Direct3D calls are counted with a plain increment instead of an atomic read‑modify‑write: about 50 thousand per race frame.

### Build 9 — the game at the screen's own resolution, sharp reflections, choices that stay
Install the APK over build 8; nothing else changes (mod packs and saves stay). Recommended: leave the phone's screen resolution where you like it (1080×2404 renders 2404×1080, 1344×2992 renders 2992×1344), Internal resolution *Native*, Reflections *Sharp*, FPS limit *60*, Anti‑aliasing *Off*, and set the game's own display settings in the game: they now stay as you leave them. To see the sharp wet‑road reflection, turn on *Road reflection* in the game's display settings.

- **Your display settings in the game stay.** *Game graphics: Maximum* wrote the game's top tier into every profile before every launch, undoing what was changed in *Customize Display Settings*. - **No more crackle on loud moments.** The game's music, engine and effects sum past full scale in races — peaks of 1.29 (2.2 dB over) in every session since build 2, tens of thousands of samples a session — and the mixer flattened them, which crackles. A look‑ahead peak limiter (2 ms look‑ahead, 250 ms release, ceiling −0.3 dBFS) now turns the mix down just before a peak instead; everything quieter passes through untouched.
- **DXVK's threads get the boost the game thread gets.** DXVK records the Vulkan half of every draw on its own command‑stream thread. The performance‑hint session that keeps the game thread's clocks up was meant to include it, but found DXVK's threads by name and DXVK's Linux code never names them, so since build 3 the session held the game thread alone. In the 20:36 session (FPS limit 60, 1080 lines) races ran at 45–50 FPS while the game thread's core averaged 1.4 GHz of the 2.46 GHz it was allowed: the thread spent much of each frame waiting. DXVK's threads are now named, join the session, stay off the game thread's core (*Fastest core* placement), and the command‑stream thread gets the game thread's priority. The summary's new *Threads* line shows it, and the CPU line now gives each core's average and peak clock.
- **Fewer lookups per Direct3D call.** Every call the game makes into Direct3D looked up its object in a hash table, and many looked up a texture or buffer as well — 25–66 thousand calls a race frame. A small cache in front of the table answers the repeated ones with one compare; the summary reports how many it answered.
- **FPS limit: 60 by default**, with labels that say what each choice costs. Races are CPU‑bound: at 120 the game thread's core runs flat out until the phone warms and its clock is capped (build 8: 92 FPS falling to about 50 within three minutes), while a 60 cap lets the launcher sleep between frames and the clocks come down. *120* is smoothest while the phone is cool; *Unlimited* is 120 with the game spinning between frames, the hottest.
- **HD cursor at the right size.** The front‑end arrow is drawn at its texture's stored size; the HD interface packs carry a 64×64 `PC_CURSOR` (stock 16×16), so where the game used that copy the arrow came out four times too large. The log now records each sound buffer's format.

One 10–15 minute session with a few races gives build 10 its targets.

### Build 8 — 120 FPS, overlapped reads, the optimised build, and smaller HD packs
Install the APK over build 6, then under *Mod packs* remove the HD interface pack (that takes the cars pack with it) and install `hdpack-v8` and `hdpack-v9`. Recommended options: Internal resolution *Native*, Texture filtering *16×*, Texture uploads *Auto*, Game graphics *Maximum*, FPS limit *120* (*Unlimited* also runs at the panel's 120, but the game then busy‑waits for each frame instead of the launcher sleeping until it, which costs heat and starves the sound threads).
- **The game ran at 60 because it chose to.** The build‑6 profile showed 13.3 billion `QueryPerformanceCounter` calls in three minutes: Speed.exe busy‑waits every frame until 1/60 s has passed (`PrepareRealTimestep`, target at `0x6F0890`), clamps the frame's time step to at least 1/60 s and adds at least one 1/60 tick per frame, so lifting the cap alone would have run the game fast. ThirteenAG's NFSUnderground.WidescreenFix carries the complete correction (on by default at the monitor's refresh rate on PC); its six patches are ported here as hooks and one data write: the limiter follows the **FPS limit** option (*Unlimited* = the 120 Hz panel), the time‑step floor becomes 1/cap, a frame shorter than 1/60 adds no tick (the remainder carries), the sound library's update runs at most every 1/60 s with the time of the frames in between passed on (those frames skip it, as on PC), particles step by the frame's real time, and the steering snap‑to‑zero below one degree (which stuck the wheels at high rates) is skipped. *60 FPS* in the launcher is the stock game's pacing.
- **Loader reads: Overlapped (default).** Reads of 64 KB and more — the loader's whole‑file reads and the 64–256 KB music/stream blocks mid‑race — now hand the guest machine to the other guest threads while the kernel copies, so they no longer freeze the render thread (build‑3 telemetry: 443 frame spikes of 20–50 ms in 27 minutes, GPU idle). This is the build‑4 change, back: it was pulled on suspicion of the profile‑menu crash that turned out to be the texture pack (below). *Hold the game during every read* restores the old behaviour for comparison.
- **Profile‑guided optimisation** from the build‑6 race session (and the build‑4 menus): the hot lifted code is laid out and inlined for how the game actually ran.
- **HD packs v8 (interface) and v9 (cars)**: the v6/v7 textures, recompressed by the toolkit's new encoder (hash chains with a lazy step, within 1 % of EA's own compressor): HUDTEX 16.2 → 13.8 MB, TSELECT 46.5 → 44.2 MB, the cars 85 → 70 MB. ### HD packs v6 (interface) and v7 (cars) — the texture tool's two bugs, found and fixed
Install both from the private releases (`hdpack-v6`, then `hdpack-v7`) after removing every earlier pack under *Mod packs*. Nothing in the APK had to change.
- **The compressor left off EA's terminator.** Every texture in a streaming pack (gauges, track previews, car textures) is its own JDLZ blob, and the game's decompressor (`sub_58D190`) counts bytes rather than tokens: it refills a flag byte the moment its 8 bits are used up — even after the last token — and copies back‑references without looking at the output size. EA's compressor ends every blob with a dummy literal token so the count comes out exactly; `tools/nfstex` didn't. In roughly one blob in eight the decoder read a byte past the stream and ran on with a negative count, writing garbage across the heap until it reached an unmapped page. That was the build‑6 crash at the profile menu (`SIGSEGV` writing at the end of a heap block from `sub_58D3F0`, the decompressor), it was the "stale sound callback" of builds 4–6 (the pointer the sound thread called through had been overwritten with texture bytes — `08ffffff080808ff…`), and v3 had 32 such blobs of its own that simply weren't loaded in the sessions that went well. The tool now reproduces the decoder byte for byte (`jdlz_game_decode`), the compressor mirrors its refills and ends with the terminator, every stock blob passes the emulation exactly as the game leaves it (one unread byte), and no pack is written unless every one of its blobs does too.
- **The parser read `INGAMEB` three bytes off.** The texture data in a bundle begins at the next 128‑byte boundary after 0x11 filler; the tool counted filler bytes instead, and `Global/INGAMEB.BUN`'s first texture happens to begin with three 0x11 bytes. Every in‑game HUD texture in packs v1–v3 was therefore upscaled from data shifted by three bytes (the rear‑view‑mirror frame decodes as noise that way). The base now comes from the alignment, as in the engine.
- Streaming‑pack records are now written exactly as EA's tools write them (field 0x34 is the aligned end of each texture's pixels; palettes sit after their textures, not first), so a stock streaming pack re‑serialises with byte‑identical info chunks — checked across all 26 of them, and every bundle in the game round‑trips byte for byte.
- The compressor now searches hash chains with a lazy step and comes out within 1 % of EA's own on the game's textures (the single‑candidate greedy version was 17–70 % larger); the v6/v7 files predate this, so the next pack release carries the same textures in 15–20 % smaller files.
- Both packs were rebuilt from the game's textures, not repacked: `hdpack.py` gained `--repack` for container‑only fixes, but v3's HUD textures needed the upscale again.
- Corrections to the build‑4 notes below: the HD cars pack was never at fault for re‑encoding uncompressed textures, and the sound library has no callback race; both were this one compressor bug seen from two sides. The DXT‑only rule for cars stays (it keeps the pack small and the lights exactly as the game shipped them), and the sound‑callback guard stays as a guard.

### Build 4 — the game's own graphics at full tier, and the profile build
- **Game graphics: Maximum (default).** The game keeps its graphics settings per profile in `NFS Underground/<profile>.cfg`, and its 2003 auto‑detect scored the port's "hardware" into a low tier: car and world reflections, the wet‑road reflection, fog, headlights, depth of field, motion blur and light streaks were all off, car detail low. Before every launch the launcher now writes the game's top tier into every profile — the values Speed.exe initialises with before the auto‑detect lowers them (`PERFORMANCE 3, ENVMAP 3, SHADOW 2, ROADREFLECTION 2, WorldLOD 3, CarLOD 1`, every effect on); resolution, colour depth and sound lines are left alone. *As set in the game's own options* leaves the files untouched.
- **Sound‑library callbacks that point at nothing are skipped, not fatal.** With the HD cars pack installed the sound library's service thread twice called through a stale pointer into memory that now holds texture data (profile menu, right after the car's textures load — a race between its 10 ms service tick and the main thread re‑registering a callback node). The runtime now skips such a call (a no‑op returning 0, logged with the bytes at the target) instead of stopping the game.
- Build 4 handed the guest machine over during reads of 64 KB and more (to stop loader and stream reads from stalling the frame); with it the sound library's service thread ran during the profile's car‑texture load and called through an unknown heap pointer on every launch (`ICALL unresolved 0x12c2ea1c from 0x652960`). Reads are atomic again as in build 3; unresolved calls now report the target bytes and the caller's registers so the next occurrence is identifiable.
- **Shader cache seed** from a 27‑minute build‑3 session (DXVK state cache and Vulkan pipeline cache), so a fresh install starts with every pipeline that session needed.
- **HD cars pack** (private `hdpack-v5`, installs on top of the interface pack): the DXT‑stored car textures in every `Cars/*/TEXTURES.BIN` — badges, grilles, trim, interiors and the DXT lights — small maps 4×, 256‑px ones 2×, same format as stored. Textures the game keeps uncompressed (most lights, the rims, door lines) are left exactly as stored: v4 re‑encoded them as DXT and the game, which works on some of them on the CPU, overran a buffer at the profile menu.
- **HD interface pack v3**: streaming packs (HUDTEX, TSELECT) keep their per‑texture JDLZ blobs and the table the engine walks when unloading them; v1/v2 crashed on the first post‑race *Continue* for want of it.
- Build `…-pgo` of this version is instrumented (`NFS_GUEST_PGO=GENERATE`): it plays a little slower and writes `files/pgo/*.profraw` on pause and exit, shipped in *Share diagnostics*. The optimised build that follows is compiled from that profile.

### Build 3 — the fast build
- **The game thread runs on the big core.** Build 2's telemetry showed the race at 45–50 FPS with the game's single busy thread parked on a mid core at ~2.7 GHz while the Cortex‑X sat idle. The render guest thread is now pinned to the fastest cluster, raised in priority, and registered in an Android performance‑hint (ADPF) session with the frame cap as its target, so the governor keeps the clock up. **CPU placement** option: *Fastest core + performance hints* (default) or *System scheduler*.
- **Fewer D3D calls reach DXVK.** A race frame issues ~45,000 device calls; render, sampler and texture‑stage states that repeat the current value are now answered in the bridge, and the device handle is resolved without a hash lookup.
- **Mod packs.** *Install mod pack (ZIP)* puts game‑relative files (Global/, Tracks/, FrontEnd/, Cars/…) over Internal storage/nfsu1, keeps every replaced original, and *Mod packs* removes them again in reverse order. This is how the HD interface pack and community data mods such as the Free Roam Mod Beta 2.0 install; programs and Speed.exe inside a ZIP are ignored.
- **HD interface pack (v2).** Built by `tools/nfstex` from the game's own textures with Real‑ESRGAN: every gauge cluster 4× (128 → 512 px), the in‑game HUD and the front end 2–4×, the 159 track‑select previews 2× (512×256 → 1024×512), the front‑end world textures 2× up to 512 px — 1,015 textures, DXT3/DXT1 with full mip chains, bundles rewritten uncompressed under the names the engine opens first (`GLOBAL\INGAMEB.LZC`, `FRONTEND\FRONTB.LZC`). Magazine covers stay stock (164 MB at 2× for a screen seen once per win). Installs through *Install mod pack (ZIP)*; about 215 MB of bundle data resident in the front end (34 MB of it in races), which the engine's growable pools take from the port's 1 GB guest arena.
- **Wrong‑way warning** option (off for free roam): blanks the HUD's wrong‑way elements the way the Free Roam Mod's own patcher does.
- Saves: the game's profile folder is `nfsu1/NFS Underground` (not `Save`); backup, restore and the diagnostics report now use it.
- Telemetry: *spikes* (frames 2.5× slower than their neighbours) replace cap‑relative hitches on the Last session card, which were meaningless while the cap was out of reach; the session record carries the thread placement result.
- Fix: the game process crashed on exit in build 2 (the session recorder raced its own sampler); the record is now written under lock after the sampler stops.

### Build 2 — the measuring build
- **Session recorder.** Every game session now writes its own complete log (`files/logs`, a logcat follower on the game process: the shared buffer had already lost the first report's game run) and a telemetry record (`files/telemetry`): frame-time distribution and 1 % lows, hitches/stalls, time inside Present, DXVK pipeline compiles (count and worst case), audio underruns, the D3D9 call profile, and a device sample every 2 s — thermal status and headroom, battery temperature, memory, CPU clocks and the panel's live refresh rate. Flushed every 30 s, so a crash keeps everything up to its last half minute.
- **Last session** card in the launcher: duration, average FPS, 1 % low, hitches, peak thermal state; tap for the full readable summary.
- **Share diagnostics** now packs the session summaries, the logs, the telemetry records, the graphics caches, `dxvk.conf`, the device state and the small `nfsu1/Save` folder (never game data).
- **Performance overlay** option: *Compact* (FPS, p99 frame time, thermal state, battery °C, top-right) or *Full* (adds DXVK's HUD: frame-time graph, GPU load, pipelines, memory).
- **Graphics log detail** option: *Verbose* makes DXVK log every shader compile for a one-off deep look.
- DXVK's information log (adapter, driver version, state-cache entries, swapchain rebuilds) now reaches the log; it used to go to a stderr nobody could read.
- **Shader cache seeded from your phone**: the state cache and the driver pipeline cache from the first Pixel 10 Pro XL session ship in the APK and are merged into the device cache before PLAY, so pipelines seen before are compiled ahead of their first frame. Each diagnostics ZIP you send grows the next build's seed.
- **Back up saves / Restore saves**: `nfsu1/Save` to a ZIP in Download/NFSU1 (share it to Drive) and back, atomically.
- Original app icon and launcher mark.
- Fix: the report's `logcat` only covered the launcher process; the launcher also captures the log tail the moment it returns from the game.
